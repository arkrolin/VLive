# V11：角色条件化（诊断 + 方案）

> 起因：R 臂（当前最佳，全量 614 / exem 先验 1.5196）abs_mae 0.9202，数字好看，但渲染出来的曲线肉眼就是不对。
> 本文记录「为什么数字好看但视觉差」的根因定位，以及由此确定的 V11 设计。
> 所有数字来自 `outputs/diag_ref_prior*.py`，口径为 **未加权原始单位 abs_mae**（与官方 span 加权的 0.9202 不同尺度，只做内部相对比较）。

---

## 1. 根因：模型只学到了幅度，没学到形状

| 口径 | exem 先验 | R 模型 | 改进 |
|---|---|---|---|
| 逐点 MAE | 1.6242 | 0.9778 | **+39.8%** |
| 一阶差分 MAE（形状） | 0.1548 | 0.1515 | **+2.1%** |

这一条解释了此前所有的困惑：

- 为什么 MAE 好看但视觉差 → MAE 由幅度主导，形状几乎没学
- 为什么预测的形状相关性（0.654）比先验（0.662）还差
- 为什么结构化低秩头（S 臂，约束形状）无效
- 为什么后处理平滑无效

**为什么学不到形状？** 因为幅度是从 rig 特征泄露进来的（见 §3），而形状需要对角色成立体化理解，held-out 角色只有 1 条 (角色, 动作) 观测，不可学。

## 2. 参考方案横评（614 val 样本，34 held-out 角色）

| 方案 | abs_mae | vs exem | vs R模型 |
|---|---|---|---|
| exem 先验（跨角色 (action,param) 均值） | 1.6242 | — | −66.1% |
| **R 模型 best（当前 SOTA）** | 0.9778 | +39.8% | — |
| 角色库·逐参数 oracle | **0.5031** | +69.0% | **+48.6%** |
| 角色库·单动作 oracle | 0.8234 | +49.3% | +15.8% |
| 它角色库·逐参数 oracle（同池大小对照） | 3.3719 | −107.6% | −244.8% |
| 跨角色同动作·逐参数 oracle（更大池，90 角色） | 1.7673 | −8.8% | −80.7% |
| 可部署检索（exem-NN 选参考动作）·逐参数 | 1.2097 | +25.5% | −23.7% |
| 可部署检索·单动作 | 1.3938 | +14.2% | −42.5% |
| delta（charmean 锚） | 1.5812 | +2.6% | −61.7% |
| 角色其它动作**均值** | 1.8510 | −14.0% | −89.3% |
| 角色 IDLE 曲线直接当先验 | 2.2758 | −40.1% | −132.7% |
| delta（IDLE 锚） | 2.2722 | −39.9% | −132.4% |
| exem × 角色幅度比 | 2.2284 | −37.2% | −127.9% |
| model/exem 逐点 oracle 门 | 0.8021 | +50.6% | +18.0% |

### 2.1 关键结论

1. **角色自身动作库是真信号，不是统计偏差。** 同池大小（~22 条）换成别的角色，误差 0.5031 vs 3.3719（6.7×）；换成更大的跨角色池（90 角色）也只有 1.7673（3.5×）。

2. ⭐ **聚合方式在跨角色 / 角色内完全相反** —— 这是架构设计的决定性依据：

   | | 平均 | 选择（oracle） | 结论 |
   |---|---|---|---|
   | 跨角色 | **1.6242** | 1.9554 | 候选之间是噪声关系，平均能抵消 |
   | 角色内 | 1.8510 | **0.5031** | 候选是语义不同的动作，选择好 3.7× |

   → **必须逐参数交叉注意力 / 软检索，任何池化、平均、单锚点都会毁掉信号。**

3. **「用角色共有的 stand 动作当锚点」被证伪。** IDLE 覆盖率 94.5%（580/614），但直接当先验 2.2758、delta 2.2722，都远差于 exem。推广版（整个库 + 选择）才成立。

4. **naive 可部署检索失败**（1.3938 vs 模型 0.9778）→ 选择函数必须是学出来的，不能用 exem 相似度硬检索。

### 2.2 增益拆解（diag_ref_prior3）

43.9% 的目标通道其实是常数（静息值）：

| 方案 | 常数通道 | 非常数通道 | 全部 |
|---|---|---|---|
| exem 先验 | 1.3069 | 1.6301 | 1.4882 |
| R 模型 | 0.7863 | 1.0132 | 0.9136 |
| 角色库·逐参数 oracle | **0.0298** | **0.7642** | 0.4417 |
| 角色库·单动作 oracle | 0.1642 | 1.2204 | 0.7566 |
| 角色静息中位数 | 0.8951 | 2.3912 | 1.7342 |

- 常数通道：exem 很差（跨角色静息值不同），角色自己的精确静息值能做到 0.03，**目前 rig 和模型都没吃干净**
- 非常数通道：单动作 oracle（1.2204）**差于模型**，必须逐参数检索（0.7642，+24.6%）

## 3. rig 96d 泄露了目标幅度

`build_model_identity` 用角色**全部动作（含目标动作）**聚合 per-param (min, max, mean)：

- 目标 range / 角色全局 range：中位 0.128、均值 0.309
- **29.2% 通道目标贡献 ≥50% 全局 range，5.2% 完全独占**

**零成本量化**（只改评估时喂给模型的 rig，权重不动）：

| 口径 | abs_mae | vs exem |
|---|---|---|
| R best + leaky rig（原报告） | 0.9202 | +39.4% |
| R best + **LOO** rig（诚实值） | **0.9481** | +37.6% |

→ 泄露值 **0.0279 = 3.0%**。真实存在但不主导。
⚠️ **R 的公平基线是 0.9481，不是 0.9202。**

## 4. 具身智能调研的对应

- 「exem 跨角色平均」= 具身智能的 **conservative averaging**（OmniXtreme 明确点名：动作库变大后策略趋向保守平均）。业内解法是 flow-matching 预训练 + **残差 RL 后训练**，不是改先验。
- **解耦范式**（OmniHumanoid 分支隔离注意力 / MotionCrafter 时空双分支 / Customize-A-Video 的 Appearance Absorber）→ 对应我们：**身份流（角色自身动作库编码）与动作语义流（标签 + 跨角色先验）显式分离**。
- MOTIF 的领域对抗（抹掉本体身份）**不适用**（我们无多本体问题）。
- VQ / 离散 token **不要抄**（MAE 下量化就是误差地板）。
- 形状口径：角色库单动作 oracle 0.2233 **差于** exem 0.1548 → **角色库单独用不给形状，必须与现有模型融合，不能替换。**

## 5. V11 设计

### V11a：角色统计特征（数据侧修复，不动架构）

1. **rig leave-one-out**：剔除目标动作对 (min, max, mean) 的贡献。新缓存存 per-param 的 `(min1, min2, max1, max2, sum, cnt)`，次小/次大值保证 LOO 极值精确；无支撑的通道置 0（未知）而非回退到泄露值。
2. **per-token 角色统计特征**（5 维，LOO 预计算）：静息值 / 典型幅度 / 下界 / 上界 / 支撑数。经**零初始化**的 `Linear(5, d)` 加进 token 嵌入 → 起步与基线逐位相同。

归一化：`rest/lo/hi` 按 `(v − lo)/span`，`amp` 按 `/span`，`log1p_cnt` 不动（clamp ±6）。

### V11b：角色动作库逐参数交叉注意力

- 每个样本携带该角色 **K=8** 条其它动作曲线（目标动作严格排除，crc32 播种保证各 DDP rank 一致）
- 参数 token 做 query，K 条参考曲线做 kv，`scores[b,p,k] = ⟨q[b,p], kv[b,k,p]⟩`
- 检索出的曲线作为**第 3 个输入通道**喂给 `in_proj`，该通道权重零初始化；`bank_gate` 零初始化标量
- 上界：逐参数 oracle 0.5031

### 验证

- `_bank_refs` 采样 K 均值 7.3 / 上限 8，**目标动作泄露 0 次**
- **no-op 逐位验证：`max|attn − base| = 0.000e+00`**
- 注意力熵 0.467（均匀应为 2.079）→ 起步即明显集中
- 梯度打开验证：head 第 1 步、`bank_gate` 与 `char_stats_enc` 第 2 步、in_proj 第 3 通道第 6 步已增长 → 分支不会训死
- ⚠️ init 时 bank 分支梯度全为 0 是**预期的**（head 也是零初始化 → out == exem → 上游无梯度）

## 6. ⭐ V11a 结果：新最佳（全量 614，2026-09-11）

| 臂 | 配置 | abs_mae | vs exem(1.5196) | vs R 公平基线 |
|---|---|---|---|---|
| **V11a** | R + rig LOO + per-token 角色统计 | **0.8720** | **+42.6%** | **+8.0%** |
| V11a latest (ep70) | 同上 | 0.8764 | +42.3% | +7.6% |
| R+rigloo（公平基线） | R best，评估时喂 LOO rig | 0.9481 | +37.6% | — |
| R（原报告，leaky rig） | R best | 0.9202 | +39.4% | — |

- **best(ep69) 0.8720 / latest(ep70) 0.8764，两者差 0.5%（噪声内）→ 已收敛，不是过拟合。**
- 训练内 117 子集：V11a 1.3667 vs R 1.4940（好 8.5%），与全量口径一致。
- **配对检验（`compare_dumps.py`，逐参数实例对齐 n=37546）**：diff = +0.0761（R 更差），**t = 2.64 → p < 0.05，显著。**
- GATE: PASS。`rel_f` 0.0106（exem 0.0143）。

### 6.1 解读

1. **V11a 是纯数据侧修复**（rig 去重 + 把角色统计显式喂给 token），**没有动架构**，却拿到了 8% 提升 —— 再次验证 §6 的判断：本项目的杠杆在数据/统计侧，不在架构侧。
2. 但提升幅度（8%）**小于** §2 里角色库 oracle 的上界（0.5031 vs 0.9778，+48.6%）——说明 per-token 5 维统计只吃掉了「静息值/幅度」这一层，**没有吃到「形状选择」那层**（§2.1 结论 2：角色内必须*选择*，不能平均/池化）。这正是 V11b 要解决的。
3. ⚠️ **此后所有比较的公平基线改为 0.9481（R+rigloo）**，0.9202 含 3.0% rig 泄露，不可用作对照。

## 7. 与历史消融的关系

架构侧改动 **0 胜 4 负**（O 门控 / P span 注入 / E 扩散 / S 低秩头）；**唯一反复验证有效的杠杆是数据**（R vs Q：1.2677 → 0.9202）。
V11 是第一个**有 oracle 数据支撑**的架构方向（0.5031 上界），此前所有架构改动都没有这样的证据。
