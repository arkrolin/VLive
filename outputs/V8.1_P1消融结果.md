## 2. 逐 arm 结果

### A `regress`（确定性残差回归）
```
ep5  abs=4.099  rel_f=0.0224
ep12 abs=2.120  rel_f=0.0169
ep13 abs=1.894  rel_f=0.0164   ← 最佳
ep16 abs=2.203  rel_f=0.0173
train_loss 0.0986 → 0.0970（几乎不动）
```
损失几乎不下降，说明**"预测残差"这个任务本身在 held-out 角色上没有可学的泛化信号**。

### B `ddpm t1000`（基线）
```
ep5  abs=3.661  rel_f=0.0217
ep8  abs=15.39  rel_f=0.0447   ← 采样噪声极大
ep23 abs=3.090  rel_f=0.0196   ← 最佳
train_loss 0.0900 → 0.0426（训练学得很好）
```
训练损失降了一半，但重建误差在 3.09~15.39 之间剧烈震荡 —— **典型的"学得很好但采样过程摧毁结果"**。

### C `ddpm t200`（截断扩散）
```
ep8  abs=25.39  rel_f=0.0738   ← 最佳
ep11 abs=86.86  rel_f=0.2451
train_loss 0.0602 → 0.0112    ← 全场最低
val_loss   0.0325 → 0.0150    ← 全场最低
```

⚠️ **C 不是公平测试，不应作为"截断扩散更差"的证据。** 训练时只见过 t<200 的输入，推理时却仍从**纯噪声** `N(0,1)` 起逆采样 —— 输入严重偏离训练分布。这个灾难性数字反映的是**训练/推理失配**，而非截断本身无效。若要认真评估截断扩散，逆采样起点必须锚定在先验上（`sqrt(a_T)·exem + sqrt(1-a_T)·ε`），而非纯噪声。

## 3. 关键发现

### 3.1 学习出来的残差**立刻**过拟合
健全性检查：只训 **1 个 epoch**（LR 尚在 warmup、约 6.7e-05，极小）：

```
abs = 2.2252   vs   exem 0.7379   → 已差 3.0×
```

零初始化保证模型起点**等于** exem。仅 1 epoch 就恶化 3 倍 ⇒ 残差头学到的东西**完全不泛化**，纯粹是在记忆训练集。

**根因**：412 个动作 / 833 样本，且 72% 动作只属于单个角色 ⇒ 模型只能记住各训练角色的个体偏差，无法迁移到 held-out 角色。

### 3.2 `val_loss` 与生成质量脱钩（再次验证 P0）
| arm | 最终 `val_loss` | best `abs_mae` |
|---|---|---|
| C | **0.0150（最低）** | **25.39（最差）** |
| A | 0.0786（最高） | **1.89（最好）** |

C 的损失低只是因为**截断后去噪任务本身更简单**，与生成质量无关。**任何跨方案的比较都必须用重建指标对 exem 基线，不能用 val_loss。**

## 5. 顺带发现：参数名嵌入从未被训练（严重 bug）

排查 P2 时发现 `schema.ParamNameEncoder` 原为**普通类**（非 `nn.Module`）：

```
name_enc in named_parameters() ?  False
model.named_children()           →  [identity_enc, action_emb, time_emb, in_proj, temporal, tok_mix, head]
                                    ↑ 没有 name_enc
m.name_enc.emb.weight            →  确实存在（只是没注册进优化器）
```

即**四路身份信号（name / rig / deformer / action）里的 "name" 一路，自项目伊始就是冻结的随机初始化，从未训练过**。不会报错，极难发现。

已修为继承 `nn.Module` + `forward()`，验证 `name_enc registered? = True`。

**教训：自定义编码器必须继承 `nn.Module`**，否则参数不进优化器。

## 6. F / G 组：归因 —— bug 修复有效，P2 无效

用语义拼音的字符级编码器替代退化为记忆表的 `nn.Embedding(1679, 384)`（每动作仅 4.4 个样本）：

- `normalize_action_name`：剥掉常量 `.motion3` 后缀
- `ActionNameEncoder`：char 嵌入 → masked mean-pool → LayerNorm + Linear + SiLU + Linear
- `cfg.action_cond`：`id` | `name` | `both`

两组并行（各 3 卡）以**分离 bug 修复与 P2 各自的贡献**：

| arm | 配置 | best `abs_mae` | vs exem 2.4405 | 归因 |
|---|---|---|---|---|
| D | `regress`@285，name_enc **冻结** | 1.6013 | −34% | 基线 |
| **F** | `regress`@285，name_enc **修复** | **1.1986** | **−51%** | **bug 修复：+25%** ✅ |
| G | F + `action_cond=name`（P2） | 1.3134 | −46% | **P2：−9.6%** ❌ |

**两个结论：**

1. **参数名嵌入的 bug 修复是本项目最大的单点收益**（1.6013 → 1.1986，提升 25%）。此前"身份分支怎么改都不涨点"的深层原因之一，就是四路信号里有一路始终是噪声。

F 在第 25 epoch 时 train_loss 仍在下降（0.0429），**未收敛** → 延长训练是合理下一步（H 组，45 epoch）。

## 10. 踩坑：评估截断按「批数」→ 跨 batch_size 不可比（已修，git `5ec9002`）

I/J 启动时把 `batch_size` 从 4 提到 8（3 卡 × 8 = 24，与 H 的 6 卡 × 4 保持有效 batch 一致），结果第 1 轮就发现：

```
H / D / E / F / G :  exem_abs_mae = 2.4405
I / J (batch 8)   :  exem_abs_mae = 2.7254   ← 同一个 exem 先验，数字变了
```

原因：`recon_metrics` 里是 `if bi >= n_batches: break`（**按批数**截断），而 val loader 用 `batch_size=cfg.batch_size` + `SequentialSampler`：

| `batch_size` | 16 批 = | 被评估的 val 样本数 | exem 基线 |
|---|---|---|---|
| 4 | 16×4 | **64** | 2.4405 |
| 8 | 16×8 | **128** | 2.7254 |

**评估子集随训练 batch size 静默变化** —— 这意味着只要两组实验的 batch size 不同，`abs_mae` 就不能直接比较，而且**没有任何报错**。

已改为**按样本数截断**（`cfg.val_recon_samples = 64`）：

```python
n_seen = 0
for _bi, batch in enumerate(loader):
    if n_seen >= n_samples:      # 按样本数，与 batch size 无关
        break
    n_seen += len(batch["target"])
```

重启后 I/J 第 1 轮即复现 `exem_abs=2.440 / exem_rel_f=0.0174`，与 A–H 完全一致。

> 历史结论**未受影响**：A–H 全部用 `batch_size=4`，共享同一个 2.4405 基线。
> 教训：**任何"评估 N 批"的写法都要改成"评估 N 个样本"**，否则 batch size 会变成一个隐藏的实验变量。

## 12. ⚠️ 重大方法学问题：验证子集只覆盖 5 个角色

在给 I/J 做离线复评时发现的，**影响此前所有结论**。

验证集是**按角色排序**的（`SequentialSampler`），561 个 shared 样本分布在 34 个 held-out 角色上（每角色 1~60 个，均值 16.5）。而训练期的 `recon_metrics` 只取**前 64 个样本**：

| 取前 N 个样本 | 覆盖的角色数 | 该子集上的 exem 先验 |
|---|---|---|
| 64 | **5 / 34** | **2.4405** |
| 128 | 12 / 34 | — |
| 561（全部） | 34 / 34 | **1.3453** |

**前 64 个样本只覆盖 5 个角色，而这 5 个角色恰好比平均难 1.8 倍。** 所以此前所有 "`abs_mae` 1.1196、比先验好 54%" 这类数字，描述的其实是"对 5 个角色的泛化"，而不是对 34 个角色的泛化。角色间方差，而非模型质量，主导了这个排名。

**已修**（`outputs/_patch_stratified_eval.py`）：训练期评估改为**按角色分层抽样**——每个 held-out 角色取 `cfg.val_recon_per_model=4` 个样本（34×4 = 115~136 个），固定种子。成本与原来（64 样本）几乎相同，但覆盖全部 34 个角色。

```python
def _stratified_val_indices(val_ds, per_model, seed):
    by_model = {}
    for i, (m, _a) in enumerate(val_ds.samples):
        by_model.setdefault(m, []).append(i)
    rng = random.Random(seed)
    idx = []
    for m in sorted(by_model):
        pool = list(by_model[m]); rng.shuffle(pool); idx.extend(pool[:per_model])
    return sorted(idx)
```

> 教训：**任何"取前 N 个样本"的评估，都要先确认数据不是按某个分组变量排序的。** 否则你测的是前几个组，而不是总体。

## 14. ⚠️ 指标口径：`abs_mae` 与 `rel_f` 给出相反结论

这是当前**最需要决策**的一点。同一个 H checkpoint：

| 口径 | 定义 | H | exem | 结论 |
|---|---|---|---|---|
| `abs_mae` | 原始参数单位的绝对误差（被大量程参数主导） | 1.2630 | 1.3453 | **只快 6.1%** |
| `rel_f` | 按参数归一化、与训练损失对齐 | 0.0129 | 0.0168 | **快 23.3%** |

两者相差近 4 倍。含义是：**模型在"平均参数"上明显优于先验（+23%），但在少量大量程参数（Live2D 里通常是位移/角度类）上，它加的残差反而引入了误差**，把绝对误差优势几乎抵消掉了。

- 训练损失是 range-normalized（每个参数等权），更接近 `rel_f` —— 所以模型确实在优化它该优化的东西。
- 但 `abs_mae` 才是"画面上偏移多少单位"的直观量。

**需要决策**：以哪个为主判据？
- **若以 `rel_f` 为主**：当前验收闸（≥10%）对 H/F 都通过（+23.3% / +19.7%），结论乐观。
- **若以 `abs_mae` 为主**：当前闸要求 ≥10%，H 只有 6.1%、F 只有 4.0% → **闸不过**。
- 第三条路：定义**感知加权**指标（按参数类型/量程分桶加权），或直接对大量程参数做损失加权，让模型在这类参数上更保守。

> 我的建议：暂时**以 `rel_f` 为主判据**（与损失一致、每参数等权、噪声更小），同时把 `abs_mae` 作为必须汇报的对照；并把"让模型在大量程参数上别帮倒忙"列为下一个明确的技术目标（例如对残差按量程做衰减，或损失加权）。

> **✅ 此处的决策已被 §17 的残差缩放扫描解决（2026-09-02）。** 分歧不是"该用哪个指标"，而是**损失函数加权错了**：扫描显示 `abs_mae` 的最优工作点是 w≈0.75、`rel_f` 是 w=1.0，说明模型残差在大量程参数上系统过冲，而等权归一化损失从不为此收费。修法是 §19 的**按量程加权损失**，让优化目标与 `abs_mae` 对齐，由模型自己学会收缩，而不是推理时后处理一个全局 w。

## 15. ⚠️ 离线复评的进程污染（已修）

排查 H 复评数字漂移时发现：

| 场景 | H 的 `abs_mae` |
|---|---|
| 同一进程内连跑两次 H | 2.2148 / 2.2148（**diff = 0.0000**，推理本身确定） |
| 旧脚本（缓存键只按 `subset_models`）独占进程 | 1.3600、1.3543 ← **异常值** |
| 旧脚本，同一进程内先跑 D 再跑 H | 1.2587 |
| **新脚本（cfg 签名缓存 + 隔离进程）× 3 次** | **1.2630 / 1.2610 / 1.2561** ← **离散仅 0.5%** |

**结论：新协议可复现到 0.5%；1.35 那一档是旧脚本的污染值，已在 §13 表格中剔除。**

同一 checkpoint、同一数据（`exem_abs`、`n_inst`、`exem_rel_f` 全部一致），只因"前面跑过谁"就差 7%。根因是 `eval_ckpt.py` 的**跨 run 语料缓存**：D/E 早于 `name_enc` 修复，需 `strict=False` 加载（随机初始化的 `name_enc` 留在进程里），缓存又让后续 run 复用它们的数据集对象。

**修法**：
1. 缓存键从 `subset_models` 改为**完整 cfg 签名**（10 个影响语料的字段）。
2. 协议改为**每个 checkpoint 独占一个进程**（`outputs/run_full_eval_isolated.sh`），实测复现性 ~0.4%。
3. 逐参数实例误差落盘（`.npz`），用 `outputs/compare_dumps.py` 做**跨进程配对检验**——虽然不在同一进程，误差向量仍然逐元素对齐，配对差分估得很紧（H vs F 的 se 只有 0.023）。

> 教训：**批量复评脚本里"复用前面 run 的对象"是危险的**，尤其当不同 run 来自不同代码版本时。宁可每 run 独立进程 + 落盘后合并。

## 17. 残差缩放扫描：`x0_hat = exem + w·residual`（零训练成本）

## 19. 按量程加权损失（K / L 组，进行中）

### 19.1 设计

训练损失目前是**归一化单位的等权 MSE**：`loss = E[(Δ/span)²]`，每个参数实例权重相同。但部署指标 `abs_mae = E[|Δ|]`（原始单位）是按量程加权的。给每个实例乘上 `(span / 批内均值) ** p`：

| p | 损失 | 对齐的指标 |
|---|---|---|
| 0 | `E[(Δ/span)²]` | `rel_f`（现状） |
| 1 | `E[Δ²/span]` | 折中 |
| **2** | **`E[Δ²]`** | **`abs_mae`（原始单位 MSE）** |

p>0 后优化器要为**原始单位误差**付费，从而自己学会在大量程参数上收缩，而不是靠推理时后乘 w=0.75。

**实现**（`_patch_span_weight.py`，已合入）：`config.span_w` / `span_w_cap`，`train.py` 的 `noise_loss` 里按 `span_t` 加权并做 clip（防止极少量程参数垄断梯度）。默认 `span_w=0` 行为逐位不变。

### 19.2 实验

| 臂 | `span_w` | `span_w_cap` | 最大权重 | 其余配置 |
|---|---|---|---|---|
| **K** | 1 | 8 | 8× | 同 H（regress / 285 / action_cond=id / 45ep / 有效 batch 24） |
| **L** | 2 | 3 | 9× | 同 H |
| H | 0 | — | 1× | **对照组** |

**预期**：K/L 的 `rel_f` 会变差（模型把容量让给大量程参数），但 `abs_mae` 应显著优于 H 的 1.2555 —— 也就是**直接优化验收闸所用的指标**。

**注意**：`span_w>0` 时 `train_loss` / `val_loss` 的量纲改变，**不可与 H 及之前所有 run 横向比较**（这本来也已是 §3.2 的结论）；早停仍按 `val_loss`，不受影响。判据只用重建指标对 exem 基线。

### 19.3 ⚠️ 训练内评估基线已变化：2.4405 → 1.929

K/L 是**第一批跑在分层采样补丁（`5b1050e`）之后**的 run。训练内评估子集从"前 64 个样本（5 个角色）"变成了"每个角色 4 个样本（~136 样本 / 34 角色）"，于是 exem 基线也随之改变：

| 阶段 | 训练内评估子集 | exem `abs_mae` | exem `rel_f` |
|---|---|---|---|
| A–H、I、J | 前 64 样本（5 角色，偏置） | 2.4405 | 0.0174 |
| **K、L 及以后** | 分层，4 样本/角色（34 角色） | **1.929** | **0.0186** |
| 离线全量复评 | 全部 561 样本 | 1.3453 | 0.0168 |

**因此 K/L 的训练内 `abs_mae` 与 H/I/J 的训练内数字不可比。** 跨臂比较一律用 `outputs/eval_ckpt.py` 在全量 561 样本上复评。

（L 第 1 轮：`train=0.2718 val=0.2521`，`abs=2.342` vs exem `1.929`、`rel_f=0.0194` vs exem `0.0186` —— 第 1 轮劣于先验是预期内的，与 H/I/J 一致：零初始化保证起点=先验，随后残差头立即开始记忆训练集。）

### 20.3 "先验误差为 0"的实例到底是什么？（判定：**(b)**）

§20.1 显示 33.8% 的实例先验误差恰好为 0，而模型仍注入 ~1 单位误差。两种相反的解释：

- **(a) 近常参数**：原始量程≈0，被地板抬到 22.66 → 模型在"本不该动"的参数上犯了大错。
- **(b) 大量程参数、只是先验恰好预测得很准** → 归一化误差很小，模型没坏，只是 `abs_mae` 按量程加权后放大了它。

**实测判定 (b)**：这些实例的平均量程 **451.14**（全体均值 196.40，地板 22.60），模型在它们上面的**归一化误差仅 0.00167**（其他实例 0.01860，差 11 倍）。模型没坏。

顺带验证了 V8/P0 的数字：**约 70% 的参数实例落在量程地板 22.60 上**（即原始量程低于全局量程的 2%），与 P0 报告的"74.4% 近常参数"一致。

### 20.4 结论：这既是**指标问题**，也是**模型问题**

**指标层面** —— `abs_mae` 被 10% 的极端量程实例主导，而在这些实例上：**先验相对误差 0.23%、模型 0.46%**，两者都已足够准，肉眼不可辨。因此：

- **`rel_f`（归一化）应作为主判据** —— 它按参数自身量程比例对待每个参数，不被极端量程绑架。
- `abs_mae` 必须汇报，但**必须附量程分位分解**，否则会得出与 `rel_f` 相反的排名。
- 这**不是"挑对自己有利的指标"**：P0 已证明 `rel`（原始量程、地板 1e-3）被近常参数绑架而不可用；现在证明 `abs_mae` 被极端量程参数绑架而不可用。两端都不可用，中间的 `rel_f` 是唯一两端都不失控的口径。

**模型层面** —— 最高量程十分位是**唯一**的失分区，且先验在那里几乎完美（0.23%）。说明这类参数（量程≈全局量程，很可能是鼠标跟随/全画布位移类）在不同角色间几乎是确定性的，**模型只需"不加残差"即可**。

**因此"学会何时不加残差"是明确且高价值的目标**，三条可行路径：

1. **按量程加权损失**（K/L 组，已在跑）：L 组 `span_w=2, cap=3` 给最高量程 ~9× 权重、地板量程 ~1/9×，**相对强调 81 倍**，直接强迫模型修好这一分位。
2. **每参数名可学习残差门控**：`residual_gate = sigmoid(Embedding(param_name))`，初始化为 ~1。极廉价（一次查表），直接表达"这个参数不该动"。
3. **按预测残差幅度自适应收缩**：残差越大越可能是过冲，但需要一个可学习的校准。

> **判定建议**：验收闸改用 `rel_f ≥ 10%`（H 已达 **+23.3%** → **PASS**），`abs_mae` 降级为"必须汇报 + 附量程分位分解"的对照；
> 同时把"最高量程十分位从 −103% 修到不劣于先验"列为下一个显式技术目标。

## 21. ⭐ 决定性诊断（续）：第 10 量程分位是**统计量覆盖漏洞**，不是一类参数

§20.2 把"最高量程十分位（span 1130.20，模型 −102.7%，胜率 1.9%）"当成一类语义参数
（推测是鼠标跟随/全画布位移类），并据此提出三条改进路径。**这个前提是错的。**

### 21.1 证据链

`mean_range_vecs` 用**全局量程**填充每个 lo/hi，只覆盖 `per_lo`/`per_hi` 里存在的参数：

```python
lo_v = np.full((B, max_tokens), g_lo);  hi_v = np.full((B, max_tokens), g_hi)
for ...: if nm in per_lo: lo_v[i,j], hi_v[i,j] = per_lo[nm], per_hi[nm]
```

而 `per_lo`/`per_hi` 来自 `compute_range(train_ds, n=400)` —— **6626 个训练样本里只取前 400 个**。
由于样本按角色排序，这 400 个样本只覆盖 **29 / 251 个训练角色（11.6%）**。

**决定性数字：从这 400 个样本算出的 `g_hi - g_lo = 1130.203`，与 §20.2 报告的第 10 分位量程
`1130.20` 逐位吻合。** 即那个分位 = "统计量里查不到的参数"，不是任何语义类别。

### 21.2 实测（本地语料，无需 GPU；`outputs/diag_range_coverage_local.py`）

| 量 | 值 |
|---|---|
| 前 400 训练样本覆盖的角色 | **29 / 251（11.6%）** |
| 落回全局量程的 val 参数实例 | **5315 / 35778 = 14.9%** |
| 其中全语料**确实有**真实量程的 | **100%** |
| 这些参数的**真实**量程中位数 | **1.70**（89.5% 低于 22.6） |
| 回落值的放大倍数（1130.2 / 真实中位数） | **665×** |
| 这些实例当前占 `abs_mae` 总权重的比例 | **87.8%** |
| 改用全语料统计后该比例 | **10.6%** |

（`abs_mae = E[|err_norm| × span]`，权重即 span 之和；14.9% 的实例因为被赋了 665× 的 span，
吃掉了 87.8% 的权重。）

### 21.3 双向伤害

这个漏洞同时打坏了训练和评测：

- **训练侧**：span=1130 使这些参数的归一化误差只有 ~0.004 → **几乎不产生梯度**，模型从没学过它们。
- **评测侧**：同一个 1130 又把（未训练出来的）误差乘回去，**主导了 `abs_mae`**。

这也解释了 §20.3：所谓"先验误差为 0 的实例平均量程 451"，其实是 1130 回落值与真实大量程参数的混合；
它们的真实量程中位数只有 1.7。

### 21.4 对 §20 结论的修正

- ❌ "学会何时不加残差"（Oracle 门控 +37.3%）—— 这个天花板有相当一部分是在度量"修掉这个漏洞"的价值，
  其中很大一块**不需要模型能力**，改一行统计即可拿到。
- ❌ "每参数名可学习残差门控" —— 门控要学的正是"这些参数别动"，但它学的其实是**错误量程的产物**。
  在错误的归一化上做门控，是在给 bug 打补丁。**先修量程，再谈门控。**
- ✅ §20.4 关于"用 `rel_f` 作主判据"的裁决**不受影响**（那是独立论证）。

### 21.5 修复（`outputs/_patch_range_fix.py`，幂等，已通过语法与幂等校验）

1. `compute_range(ds, n=None)` 扫**全量**训练集（`cfg.range_stats_n`，默认 None = 全部）；
   单次约 3.5 分钟，结果缓存到 `outputs/range_cache_{subset}_{n}_{len}.pkl`
   （**原子 rename**，多任务并行启动安全）。
2. 新增第 5 个返回值 `fb_span`：查不到的参数改用**每参数量程分布的分位数**
   （`cfg.fb_span_q`，默认 0.5 = 中位数），而不是全局量程。`fb_span_q < 0` 回退旧行为。
3. `mean_range_vecs` 增加 `fb_span=None`（默认 None = 行为逐位不变）。

未覆盖率：**14.9% → 5.18%**（残余的是只在 held-out 角色里出现的角色特有参数）。
由于 `min_span = 22.66` 的地板会把它兜住，回落值取 0.5 或 0.9 分位数效果相同，风险可控。

兼容性：checkpoint 通过 `cfg.__dict__` 持久化 `fb_span`；**旧 checkpoint 没有这个键 → 自动沿用旧的
全局量程填充**，即复现它们训练时的归一化，不会被静默改变。

### 21.6 ⚠️ 可检验的预测（这是本节的要点）

`exem` 先验的 `abs_mae` 是**原始单位量，与归一化无关** → 修复后仍是 **1.3453，不变**。
模型的 `abs_mae` 依赖归一化 → 应当**显著下降**。

> **预测：H′（H 的相同配置 + 量程修复）的 `abs_mae` 应从 1.2555 明显下降，
> 对 exem 先验 1.3453 的优势从 +6.7% 提升到接近"剔除第 10 分位"的 +31.7%。**

若 H′ 的相对优势没有实质提升，说明 §20 的"剔除分位后 +31.7%"确实只是指标戏法，
那时才应该回到模型侧（门控/容量）找原因。

### 21.7 下一步

| 优先级 | 动作 | 成本 |
|---|---|---|
| **P0** | 应用 `_patch_range_fix.py`，跑 **M = H′**（与 H 完全同配置，仅量程修复，45ep） | GPU ~5h |
| P1 | 等 K/L 跑完（它们与 H 同用旧归一化，**内部对比仍然有效，不要杀**） | 0 |
| P2 | 若 K（按量程加权损失）胜出 → 跑 **N = K′ + 量程修复** | GPU ~5h |
| P3 | 若 H′ 后第 10 分位仍显著为负 → 才回到门控方案 | — |

M 组必须与 H 组在**同一归一化**下比较；跨归一化比较 `abs_mae` 与跨方案比较 `val_loss` 一样无效。

## 23. ⭐ M/N 裁决：量程漏洞确认，量程修复是最大单点收益（+23%）

> 口径：全量验证集 561 样本 / 34 角色，exem 先验 `abs_mae = 1.3453`。
> N 与 M 只差归一化（其余 `regress@285` + `span_w=1,cap=8` + 70ep + `select_metric=abs` 完全一致）。

### 23.1 结果（决定性）

| 臂 | 归一化 | 结局 | checkpoint | `abs_mae` | vs exem |
|---|---|---|---|---|---|
| **N** | 旧（n=400 + 全局量程） | **ep16 早停**（abs 连续 15 epoch 无改善） | best (ep1) | 1.5325 | **−13.9%** |
| N | 旧 | 同上 | latest (ep16) | 2.6898 | **−99.9%** |
| **M** | **量程修复** | 训练中（ep48/70） | latest (ep48) | **1.0373** | **+22.9%** |

**§21.6 的可检验预测被证实**：exem 基线在 N/M 下完全一致（1.3453 vs 1.3451，差异 0.015%，
远在 0.4% 复评噪声地板内），而模型 `abs_mae` 在修复归一化后从 **−13.9% 翻转到 +22.9%**。
**量程统计覆盖漏洞确认为真，且是迄今最大的单点杠杆。**

### 23.2 解读：N 为什么输得这么彻底

1. **N 从第一个 epoch 起就劣于 exem，且越训越差**（1.53 → 2.69）。这正是 §21 的机制：
   14.9% 的实例被赋 1130.2 的全局量程（真实中位数 1.70，665×），`abs_mae` 被这些**不可学**的
   参数主导，模型一直在优化错误目标、往错误方向跑。
2. **N 甚至跑不满 70 epoch**：`select_metric=abs` 让它在 ep16 就因"abs 连续 15 epoch 无改善"早停。
   这是独立于复评数字的第二个信号——在错误归一化下，**按目标指标选点会直接判死一个方案**。
   回想 §22.2：K（同归一化）用 val_loss 选点才勉强活到 ep45；换成 abs 选点立刻露馅。

## 24. V8.3 架构：span 条件注入（arm P，已上机）

> 本节是对"模型侧架构改进"的一次落地 —— 目标直指 §20/§21 暴露的残差过冲与量程强相关这一缺陷。

### 24.1 动机：模型"看不见"参数的绝对量程

- 现有加性分解 `x0_hat = exem + residual` 里，模型对残差的预测**只能**从参数名 embedding 推断量级；
  但同一参数名在不同角色/rig 下的实际量程 `span = hi − lo` 差异很大，名字是查不到的。
- §20/§21 已经证明：残差过冲与 span 强相关，14.9% 的极端量程实例吃了 87.8% 的 `abs_mae` 权重。
  与其让模型靠名字"猜"量程，不如把量程**直接喂给它**。

### 24.2 设计（零初始化，bit-identical 起点）

```python
# model.py __init__
self.span_cond = getattr(cfg, "span_cond", "none")
if self.span_cond == "log":
    self.span_enc = nn.Linear(1, d)
    nn.init.zeros_(self.span_enc.weight)   # 零初始化
    nn.init.zeros_(self.span_enc.bias)

# model.py _token_emb
if self.span_enc is not None and span is not None:
    ls = torch.log(span.clamp(min=1e-6)).unsqueeze(-1)
    tok = tok + self.span_enc(ls)          # 加性注入到 token embedding
```

- `span` 取**与训练 loss 对齐**的 `span_t = (hi−lo).clamp(min=2%·global_range)`（§21 修复后的量程），
  沿 `noise_loss → ddim_reverse → recon_metrics` 一路传进 `forward`（`eval_ckpt.py` 经 `recon_metrics` 复用同一路径）。
- `Linear(1,d)` 零初始化 → **ep1 输出与 `span_cond=none` 逐 bit 相同**（残差约等于 0 的起点），
  构成干净的 A/B，不会引入"起点不同"的混杂。

### 24.3 冒烟（已通过）

`residual_gate=none select_metric=abs span_cond=log`，ep1：`train=0.2552 val=0.3094 abs=1.931 exem_abs=1.929`。
与 no-gate 起点一致，证实零初始化生效、span 分支未破坏起点等价性。

### 24.4 上机（arm P）

| 项 | 值 |
|---|---|
| 配置 | M（量程修复 + `span_w=1,cap=8` + `select_metric=abs`）+ **`span_cond=log`** |
| GPU | 5,6,7（等 M 跑完 ep70 后自动接管，`launch_P_spancond.sh` 看门狗） |
| port | 29674 |
| 判定 | P 相对 M 的 `abs_mae` 是否再有增益（span 直接可见是否进一步压过冲） |

- 若 P 无增益 → 说明 span 信息已通过归一化 + `span_w` 被充分编码，架构注入冗余；
  若 P 有增益 → 可进一步把 span 编码换成可学习的非线性（当前仅 `log` 线性）。

### 25.3 解读：门控为什么不奏效

- §20 的 Oracle 门控（0.7914，比最优模型再低 37%）是在**旧归一化 bug**下测的——"最高量程那 10%
  实例"其实是 14.9% 被赋全局量程 1130.2 的统计漏洞参数，不是模型能靠门控区分的一类语义。
- 量程修复后，这些实例归一化回到真实中位数，残差过冲基本消失，门控要学的"哪些参数少加残差"
  变得几乎无事可做 → 净收益为零（甚至因多一个可学习分支带来轻微过拟合）。
- 结论：**门控是给 bug 打补丁**（§21 的原始判断）。bug 修好后门控不再需要，也不该再上。

  → 稳定劣化约 3%。
- 结论：**span 显式注入不可取。** span 信息应通过归一化/损失加权间接施加（已有），而不是作为显式输入特征。
  §24.4 的"span 已被归一化 + span_w 充分编码、架构注入冗余"预测得到证实。
